# CAN-AI Actuator Lab 🚘💡

**An AI writes a fresh "CAN control program" on every request → it passes a safety review → it drives the car's ambient‑lighting actuators.**

**AIが毎回「CAN制御プログラム」を生成 → 安全審査を通過 → 車内アンビエント照明アクチュエータを制御する。**

🌐 **Live demo (GitHub Pages):** `https://togakyo.github.io/scratch-car-interior/`

## English

### Concept — "the AI writes the actuator‑switching code every time"

Instead of hard‑coded control, the **control program itself is generated by an AI** from the user's intent.
But letting an AI emit arbitrary bytes onto a vehicle bus is dangerous, so this project **confines the AI's output to a safe representation and always inspects it before execution.**

```
① Intent (natural language)
      │  e.g. "gently light the footwells white when a door opens"
      ▼
② AI planner ────────►  emits ONLY a lighting DSL (JSON)
      │                  (cannot write CAN IDs or raw bytes — structural sandbox)
      ▼
③ Trusted compiler ──►  DSL → CAN frames
      │                  (only this layer knows CAN IDs; output limited to ambient IDs)
      ▼
④ Safety supervisor ─►  inspects every frame: pass / clamp / reject
      │                  (verdict depends on vehicle state: parked vs. driving)
      ▼
⑤ Virtual CAN bus → ECU model → in‑cabin illumination
```

### Why defense‑in‑depth

| Layer | Role | Safety meaning |
|-------|------|----------------|
| **DSL sandbox** | The AI can only express color / brightness / effect / zone | Even a rogue AI **cannot emit brake or steering IDs** |
| **Trusted compiler** | The only trusted code that turns DSL into CAN | Generated IDs are **structurally limited** to ambient `0x3C0..0x3C6 / 0x3BF` |
| **Safety supervisor** | Validates / clamps / rejects every frame just before TX | ID allowlist, brightness caps, flash‑rate caps, driving policy, watchdog |
| **E‑STOP** | Instantly turns all zones off | A guaranteed path back to a safe state |

### Safety policy (implemented in `docs/src/safety.js`)

Verdicts depend on **vehicle state (speed / gear)**:

- **CAN ID allowlist** — any non‑ambient ID (e.g. powertrain/brake) is **REJECTED** unconditionally (defense‑in‑depth double check)
- **Message integrity** — rolling counter + checksum mismatch → **REJECT**
- **Flash‑frequency cap** — photosensitivity guard: 5 Hz always, 3 Hz while driving → **CLAMP**
- **Forward‑field zones while driving** — glare guard clamps brightness; flashing is downgraded to "breathe"
- **Red flashing while driving** — banned on all zones (mistaken for a warning lamp) → **REJECT**
- **Watchdog** — program duration clamped to 30 s; `endState:off` forces an all‑off tail (fail‑safe)

These are covered by unit tests → `test/safety.test.mjs`.

### 🤖 Run a real lightweight model on your own PC

By default the demo uses an **offline rule‑based planner** (works on GitHub Pages with no backend).
You can switch to a **real lightweight LLM downloaded from Hugging Face and run locally on your PC**
(default: `Qwen/Qwen2.5-0.5B-Instruct`, Apache‑2.0, runs on CPU; auto‑uses CUDA/Apple‑Silicon MPS if present).

```bash
pip install -r ai/requirements.txt
python ai/planner_server.py          # downloads the model on first run, serves on :8000
# quick check without downloading a model:
python ai/planner_server.py --mock   # rule-based only
```

Then open the page, pick **"ローカルAI (Local AI)"** in the planner selector, and generate.
The model **is not trusted**: its JSON output is repaired by `normalizeDsl()`, then lowered by the
compiler and screened by the safety supervisor. If the server is down, the UI **falls back to the
rule‑based planner automatically**, so the hosted demo always works.

```
POST http://localhost:8000/plan   {"intent": "..."} → {"dsl": {...}, "source": "llm"|"fallback", "model": "..."}
GET  http://localhost:8000/health                    → {"status":"ok","model":"...","device":"cpu|mps|cuda"}
```

### CAN signals (a single comfort-domain node only)

| ID | Message | Contents |
|----|---------|----------|
| `0x0C0` | `VEHICLE_STATE` | ignition / gear / speed / doors — **read only** |
| `0x3BF` | `ALM_GLOBAL_CMD` | master brightness / all-off (E-STOP) |
| `0x3C0..0x3C6` | `ALM_ZONE_CMD` | per zone: `[R,G,B,brightness,effect,speed,reserved,counter|CRC]` |

Zones: footwell L/R, door L/R, dashboard, center console, cupholder.

### Small start toward real hardware

1. **Planner → real LLM:** already done — `ai/planner_server.py` runs a local HF model. Swap in a larger
   model with `--model`, or point `LlmPlanner`'s endpoint at your own service (same DSL contract).
2. **Virtual bus → real CAN:** replace `VirtualCanBus` with SocketCAN (`can0`) / `python-can` / a CAN‑USB adapter;
   only the `send(frame)` body changes (keep the safety review before TX).
3. **Actuator → real ECU:** drive an RGB LED strip from a microcontroller (e.g. Raspberry Pi + MCP2515) that
   consumes `ALM_ZONE_CMD`. Starting from a **non‑safety actuator (lighting)** is the safe small start.

> ⚠️ Do not connect to a real vehicle bus. This is meant for a bench setup (an isolated CAN bus + LEDs).

## 日本語

### コンセプト — 「アクチュエータを切り替えるコードを、AIが毎回書く」

固定のハードコードではなく、ユーザーの意図に応じて **制御プログラムそのものをAIが生成** します。
ただし車載で「AIが自由にバイト列を送れる」ことは危険なので、**AIの出力を安全な表現に閉じ込め、実行前に必ず検査する** 構成にしています。

```
① 意図（自然言語）
      │  例）「ドアを開けたら足元を白くゆっくり点灯」
      ▼
② AIプランナー ──────►  照明DSL(JSON) だけを生成
      │                  （CAN ID・生バイト列は書けない＝構造的サンドボックス）
      ▼
③ 信頼コンパイラ ────►  DSL → CANフレーム へ変換
      │                  （ここだけがCAN IDを知る。生成先はアンビエント系IDに限定）
      ▼
④ セーフティ・スーパーバイザー ─►  1フレームずつ検査: pass / clamp / reject
      │                  （判定は車両状態=停車/走行に依存）
      ▼
⑤ 仮想CANバス → ECUモデル → 車内イルミ
```

### なぜ「多層防御」なのか

| 層 | 役割 | 安全上の意味 |
|----|------|------|
| **DSLサンドボックス** | AIは色/輝度/エフェクト/ゾーンしか表現できない | AIが暴走しても、そもそも**ブレーキやステアのIDを発火できない** |
| **信頼コンパイラ** | DSL→CAN変換を担う唯一の信頼コード | 生成IDはアンビエント系 `0x3C0..0x3C6 / 0x3BF` に**構造的に限定** |
| **安全審査** | 実行直前に全フレームを検証・クランプ・破棄 | ID allowlist / 輝度上限 / 点滅周波数 / 走行中ポリシー / ウォッチドッグ |
| **E-STOP** | 全ゾーン即時消灯のフェイルセーフ | いつでも安全状態へ復帰可能 |

### 安全審査ポリシー（`docs/src/safety.js` に実装）

判定は **車両状態（速度・ギア）** に依存します。

- **CAN ID allowlist** — 許可外ID（例: パワトレ/ブレーキ系）は無条件 **REJECT**（多層防御の二重チェック）
- **メッセージ完全性** — ローリングカウンタ＋チェックサム不一致は **REJECT**
- **点滅周波数の上限** — 光過敏対策。常時 5Hz、走行中は 3Hz を超えると **CLAMP**
- **前方視野ゾーンの制限（走行中）** — グレア対策で輝度を上限へ **CLAMP**、点滅は「呼吸」へ格下げ
- **赤色点滅の禁止（走行中）** — 警告表示との誤認防止のため全ゾーンで **REJECT**
- **ウォッチドッグ** — 継続時間を 30s へ **CLAMP**、`endState:off` は末尾に全消灯を強制付与

これらは単体テストで検証しています → `test/safety.test.mjs`

切り替えると、**Hugging Faceからダウンロードした軽量LLMを自分のPC上でローカル実行** できます
（既定: `Qwen/Qwen2.5-0.5B-Instruct`、Apache‑2.0、CPUで動作。CUDA / Apple Silicon(MPS) があれば自動利用）。

```bash

サーバ未起動時は **自動的に規則ベースへフォールバック** するので、公開デモは常に動作します。

```
POST http://localhost:8000/plan   {"intent":"…"} → {"dsl":{…},"source":"llm"|"fallback","model":"…"}

（実測: Apple Silicon で初回ロード ≒ 60秒、以降の生成は 1〜6秒/件。）

### 実機へのスモールスタート

1. **プランナーを実LLMへ** — 実装済み。`ai/planner_server.py` がローカルHFモデルを実行。`--model` で大きいモデルに変更、または `LlmPlanner` のエンドポイントを自前サービスに向ける（DSL契約は同一）。
2. **仮想バスを実CANへ** — `VirtualCanBus` を SocketCAN(`can0`) / `python-can` / CAN-USB に置換。`send(frame)` の中身を変えるだけ（安全審査は送信前のまま維持）。
3. **アクチュエータを実ECUへ** — RGB LEDストリップ＋マイコン（例: Raspberry Pi + MCP2515）で `ALM_ZONE_CMD` を受けて点灯。**照明という非安全アクチュエータ**から始めるのが安全なスモールスタート。

> ⚠️ 実車両のバスには接続しないでください。ベンチ環境（独立したCANバス＋LED）での検証を前提としています。
